AIML context file
=================

Purpose
-------
This file records project knowledge that should not have to be re-derived every time during analysis,
debugging, compiler work and test design. It is deliberately pragmatic and is meant to prevent typical
false assumptions.


Important ground rules
----------------------

1. Do not infer AIML behaviour from general language intuition.
   AIML has several peculiarities that differ from typical scripting languages, C++, Python or YAML-
   embedded DSLs. Always look at the real compiler path and existing repros.

2. Spec and implementation are not congruent.
   The spec is broader than the current implementation. When in doubt:
   - check the real code path first
   - then read existing reports and repros
   - only then make new statements

3. Do not silently read "modern" or "obvious" semantics into it.
   If a detail is not verified, do not guess.


Particularly important AIML facts
---------------------------------

1. string.len is not a property but a method.
   Correct:
   - { call: [my_string.len] }

   Wrong:
   - my_string.len as an attribute value

   Important note:
   - The spec differentiated between .len and .size, but in real discussions exactly
     this point has often been mixed up.
   - Before making statements about len/size/string/list/map, always check the current implementation state.

2. Not every "dot" can be nested freely.
   Deep member chains like a.b.c or deep set targets do not work robustly throughout in AIML.
   That is exactly why there are many helper variables and whole-object reassigns.

3. Imported globals do not automatically behave like cleanly shared module variables.
   There have already been real problems with multiple definitions and `extern` semantics.
   So for global state across files never blindly assume:
   - "it is surely the same instance"
   - "import will do this correctly"

4. JIT and AOT are not automatically semantically identical.
   `compile()` and string/chunk paths do not run through exactly the same compiler context.

5. Do not idealise mirror/WebSocket semantics.
   `session.update()` was already narrower in real behaviour than the intuitive expectation.
   Queue drain, event order and WS framing must always be checked against real repros.


Models, heap and serialisation
------------------------------

1. AIML builtins and runtime paths take care of heap-carried pointers in several places.
   That concerns in particular:
   - serialisation
   - mirror sync
   - model passing

   It is therefore wrong to assume across the board:
   - "pointer-based models cannot be serialised"
   - "only stack-like values go through mirror"

2. Still, never blindly assume that every pointer case is correct.
   The right working hypothesis is:
   - There is already runtime support for pointer/heap objects in builtins.
   - Whether a concrete case works must be verified on the real C++ path and a repro.

3. For model sync and serialisation always separate:
   - what the language model promises
   - what the current runtime really handles correctly

4. When an error shows up in serialisation or mirror, first distinguish these levels:
   - the compiler generates a wrong access
   - the runtime serialises wrong fields
   - the runtime decodes wrongly
   - the test uses the object too early
   - debug code only crashes while logging


Function calls and types
------------------------

1. The compiler does not always report type errors in function parameters strictly enough.
   Do not presuppose that a wrong parameter type immediately ends as a clean compiler error.

2. Builtins often have softer or more special conversion paths than user functions.
   Statements about "AIML can pass X to function Y" must distinguish between
   - general language behaviour
   - a builtin special case

3. Do not romanticise `map<string:any>`, structure and model passing.
   The spec promises more here than the current compiler guarantees in all places.


Collections, len/size and access
--------------------------------

1. Do not mix up `len` and `size`.
   Before every statement check whether what is meant is
   - an element/character count
   - a byte size

2. For collections and strings never conclude from the syntax alone.
   Some things look like properties, others like methods. When in doubt, check real usage in the project
   and the compiler/builtin implementation.

3. Do not guess null and missing-key behaviour.
   Exactly these points have already been vague several times in the spec and in implementation discussions.


Mirror and sync
---------------

1. For mirror problems never look only at the AIML script.
   Always keep these levels in mind as well:
   - `builtin_registry.cpp`
   - `mirror_runtime.cpp`
   - generated model/serializer paths

2. Do not claim "register_id broken" or "GameView is not registered" too quickly.
   Several earlier cases were in truth:
   - use too early after registration
   - updates not yet drained
   - a debug crash in the C++ logging
   - the test does not cover the real case

3. Mirror tests must recreate real use cases.
   Especially for 9rooms-like cases:
   - early empty registration
   - later filling
   - counter-registration from the client
   - several update() ticks


How to proceed when unsure
--------------------------

1. Before every strong claim, read the real code path first.

2. Before every language claim, check:
   - is there already a report?
   - is there already a repro?
   - is there already a test?

3. If something seems counter-intuitive, in AIML the right reaction often is:
   - do not reinterpret
   - not "probably like in language X"
   - but verify concretely

4. On recurring doubts, extend this file instead of making the same mistakes again.


Maxims
------

- Do not guess. Verify.
- The spec is not automatically runtime truth.
- Builtin behaviour is not automatically general language semantics.
- Deep member paths are suspect until proven otherwise.
- Mirror errors often do not sit where the AIML script suspects them.
