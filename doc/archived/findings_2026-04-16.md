# Findings 2026-04-16

## Context

This file summarises the review findings for the AIML/TUL code base and derives a concrete improvement plan from them. Focus:

- efficiency
- memory management
- DB access
- generative AI / tensor and sampling paths

## 1. Make Store<T> thread-safe

Affected places:

- `src/sys/db_runtime.cpp:39`
- `src/sys/db_runtime.cpp:493`
- `src/sys/db_runtime.cpp:535`
- `src/sys/db_runtime.cpp:567`
- `src/sys/db_runtime.cpp:611`
- `src/sys/db_runtime.cpp:648`

Problem:

- `AimlStore` has no per-store lock.
- `insert`, `update`, `get`, `delete`, `checkpoint`, `mmap` resize and WAL replay can access the same state in parallel.
- That endangers `vector` memory, `mmap` pointers, header counters and WAL consistency.

Plan:

1. Introduce `std::mutex mtx;` in `AimlStore`.
2. Secure all hot-path methods with `std::lock_guard<std::mutex>`.
3. Only run `store_mmap_extend()` and `store_wal_replay()` under the same lock.
4. After that optionally switch to `std::shared_mutex` if read-heavy patterns justify it.
5. Add multithreaded tests with parallel `insert/get/update/delete`.

## 2. Synchronise VecStore correctly

Affected places:

- `src/sys/db_runtime.cpp:88`
- `src/sys/db_runtime.cpp:1124`
- `src/sys/db_runtime.cpp:1142`
- `src/sys/db_runtime.cpp:1161`

Problem:

- `AimlVecStore` owns a mutex, but `insert` and `search` do not use it.
- `search` reads while `ids` and `embeddings` can grow through `insert`.
- The return uses `c_str()` on an internal `std::string` that can move on reallocation.

Plan:

1. Secure `aiml_db_vec_insert()` with `std::lock_guard<std::mutex>`.
2. Also lock `aiml_db_vec_search()` or create a stable snapshot before the search.
3. Do not bind `VecResult.id` directly to `c_str()`, but copy it.
4. Introduce an API for freeing search results.
5. Add parallel tests for `insert + search + checkpoint`.

## 3. Fix the string KV leak on overwrite

Affected places:

- `src/sys/db_runtime.cpp:919`
- `src/sys/db_runtime.cpp:937`

Problem:

- In the string branch new heap is allocated via `strdup` on every `set`.
- An old value for the same key is not freed before replacement.

Plan:

1. In `aiml_db_kv_set()` look up the old key before writing.
2. If the old entry is in string mode, read the old `char*` and call `free()`.
3. Only after that duplicate and store the new string.
4. Add a test with frequent overwriting of the same key.

## 4. Secure AI sampling and embedding access

Affected places:

- `src/sys/ai_runtime.cpp:14`
- `src/sys/ai_runtime.cpp:21`
- `src/sys/ai_runtime.cpp:37`
- `src/sys/ai_runtime.cpp:53`
- `src/sys/ai_runtime.cpp:112`

Problem:

- `sample_logits()` does not validate `temperature`.
- `rand()` / `srand()` are weak for parallel or reproducible GenAI paths.
- Embedding accesses do not check `token_id` against a valid vocabulary bound.

Plan:

1. Catch `temperature <= 0` hard.
2. Detect NaN/Inf paths after softmax and fall back to `argmax`.
3. Use `thread_local std::mt19937` plus `std::uniform_real_distribution<float>`.
4. Extend the embedding APIs by `vocab_size` or validated tensor metadata.
5. Add tests for negative token IDs, too large token IDs and borderline temperatures.

## 5. Make BPE training more scalable

Affected places:

- `src/sys/ai_runtime.cpp:167`

Problem:

- The merge loop scans `pairCounts` completely and then runs over all words.
- `vector.erase()` in the inner loop is expensive for large corpora.

Plan:

1. Introduce a max-heap for the most frequent pairs.
2. Recompute merge updates incrementally instead of globally.
3. Represent symbol sequences more compactly to reduce expensive `erase` operations.
4. Treat BPE training clearly as an offline path.

## 6. Make tensor allocation robust

Affected places:

- `src/sys/tensor_runtime.cpp:169`
- `src/sys/tensor_runtime.cpp:176`

Problem:

- `compute_size()` uses `int` and is thus prone to overflow.
- `alloc_tensor()` logs on a failed `malloc`, but still passes on a half-initialised object.

Plan:

1. Switch the size computation to `int64_t` or `size_t`.
2. Check for overflow explicitly before `malloc/calloc`.
3. On allocation failure clean up properly and return `nullptr`.
4. Make all public tensor entry points robust against `nullptr`.

## 7. Harden the tensor life cycle further

Affected places:

- `src/sys/tensor_runtime.cpp:1093`
- `src/sys/tensor_runtime.cpp:1154`

Problem:

- The basic structure is good, but ownership is modelled via loose flags.
- That makes later special cases for arena, heap, views and DB-bound tensors error-prone.

Plan:

1. Introduce an ownership enum, e.g. `TensorStorageKind`.
2. Align `aiml_tensor_free()` and `aiml_tensor_thread_cleanup()` with this enum.
3. Mark DB-bound/view tensors explicitly.
4. Add life cycle tests for arena, heap, clone and DB-bound tensors.

## 8. Index DB key access

Affected places:

- `src/sys/db_runtime.cpp:589`

Problem:

- `aiml_db_store_get_by_key()` does a full scan over all slots.
- That quickly becomes a bottleneck for relational or agentic workloads.

Plan:

1. Introduce an optional hash index in `AimlStore`.
2. Extend the API so that indexed fields can be defined at open.
3. Maintain the index in `insert/update/delete`.
4. Run `get_by_key()` via the index first, and only as a fallback via a full scan.

## 9. Improve vector search architecturally

Affected places:

- `src/sys/db_runtime.cpp:1161`

Problem:

- The search path is brute force over all embeddings.
- The storage structure `vector<vector<float>>` is cache-inefficient.
- Heap is newly allocated per hit.

Plan:

1. Store embeddings as a flat matrix.
2. Cache norms per embedding at insert.
3. Compute the query norm once per search.
4. In the medium term introduce an ANN structure, e.g. HNSW or IVF.
5. Pool return objects or write into a preallocated result structure.

## 10. Make WAL and persistence more robust

Affected places:

- `src/sys/db_runtime.cpp:176`
- `src/sys/db_runtime.cpp:233`
- `src/sys/db_runtime.cpp:744`
- `src/sys/db_runtime.cpp:1124`

Problem:

- Partial I/O is often not fully validated.
- The WAL has no CRC or record integrity.
- Recovery from truncated files is only secured to a limited extent.

Plan:

1. Fully validate the return values of `read/write`.
2. Introduce a record header with length and CRC.
3. Make the fsync policy configurable.
4. Extend version numbers for WAL formats.
5. Add crash/truncate recovery tests.

## 11. Make the mirror runtime more efficient

Affected places:

- `src/sys/mirror_runtime.cpp:1`
- `src/sys/mirror_runtime.cpp:91`

Problem:

- Dirty tracking is still largely based on whole-struct/whole-blob comparison.
- That is simple in terms of correctness, but expensive for large models and high sync frequency.

Plan:

1. Introduce field masks or dirty bits.
2. Make typed delta serialisation incremental.
3. Integrate payload lengths and optional compression cleanly into the network path.
4. Benchmark mirror paths: small models, large models, high event rate.

## 12. Improve analyzer scaling in the Exodus tooling

Affected places:

- `../exodus/exodus/tools/analyze/analyze.py:121`
- `../exodus/exodus/tools/analyze/analyze.py:222`

Problem:

- The cross-TU heuristic keeps a lot of state in RAM.
- Symbol detection often scans file content several times.

Plan:

1. Invert file scans: analyse per file instead of per symbol.
2. Bound or stream large text caches.
3. Move more preparatory work into Clang workers.

## Recommended order

1. `Store<T>` locking
2. `VecStore` locking
3. String KV leak
4. AI sampling + token validation
5. Tensor allocator robustness
6. `get_by_key()` index
7. Vector search redesign
8. WAL hardening
9. Mirror optimisation

## Short conclusion

The code base is already well above prototype level. The biggest lever now no longer lies in new features, but in:

- consistent thread safety
- stable memory management
- more efficient data structures for DB and retrieval
- harder guards in the generative runtime paths
